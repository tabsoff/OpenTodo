# Как вносить изменения в OpenTodo

Репозиторий вашей версии: https://github.com/tabsoff/OpenTodo

Рабочее приложение: https://todo.tabsoff.ru

Тестовое приложение: https://todo-test.tabsoff.ru

Данные входа хранятся отдельно и в репозиторий не добавляются. Сначала браузер попросит логин защиты сайта, затем — вход в сам OpenTodo. У тестового приложения отдельный аккаунт и отдельные задачи.

## Когда нужна доработка

1. Опишите мне изменение и ожидаемое поведение.
2. Я запускаю локальный предпросмотр на вашем компьютере с отдельной тестовой базой. Вы открываете его в браузере по локальному адресу. Мы вносим правки и сразу смотрим результат: интерфейс обновляется автоматически, а изменения серверной части могут требовать перезапуска локального сервера.
3. После вашего одобрения локального результата оформляется запрос на слияние в ветку `tabsoff` и запускаются обязательные проверки. После слияния GitHub собирает приложение и обновляет тестовый сайт. Изменения только серверных сценариев проходят короткий набор проверок без пересборки приложения. На VPS ничего компилировать не нужно.
4. Вы проверяете результат на тестовом сайте с тестовыми задачами.
5. Для рабочего выпуска откройте **GitHub → Actions → Tabsoff production → Run workflow**, выберите ветку `tabsoff` и действие `promote`. Сценарий сам выберет текущую проверенную тестовую сборку и покажет её перед подтверждением владельца для окружения `production`. Копировать технические идентификаторы больше не требуется. Если тестовая версия успеет смениться, выпуск остановится — потребуется повторный запуск и проверка выбранной версии.

Основной формат согласован 23 октября 2026 года: **правки → локальный просмотр → ваше одобрение → PR и проверки → тестовый сайт → решение о рабочем выпуске**.

Для каждой промежуточной правки не нужны полный GitHub CI, новый PR или загрузка на VPS. Нужные для изменения локальные проверки выполняются по мере работы. Требования репозитория к спецификациям и проверкам перед выпуском сохраняются.

Локальный предпросмотр доступен только через localhost и использует отдельные тестовые данные. Рабочие данные и учётные записи для экспериментов не используются. Локальное окружение пока не настроено; его нужно подготовить и проверить перед первой доработкой. Одобрение локального результата само по себе не разрешает рабочий выпуск.

На рабочий сайт поступает тот же образ, который был проверен на тестовом. Перед обновлением сохраняются старая версия и её данные. При неудачном запуске они восстанавливаются вместе.

Для повторной выкладки после сбоя вручную запустите **Tabsoff staging** и укажите полный идентификатор коммита из успешного запуска CI, опубликовавшего образ. Он берёт уже проверенную сборку и повторяет только её тестовое развёртывание, без новой публикации образа. Тот же сценарий используется автоматически после изменений приложения.

## Официальные обновления

Ежедневная проверка ищет новый стабильный релиз автора и предлагает его отдельным запросом на слияние. Ваши доработки сохраняются в собственной ветке. Если изменения пересекаются, конфликт нужно разрешить до выпуска.

Дальше порядок тот же: проверки → тестовый сайт → ваше решение → рабочий выпуск. Официальное обновление само по себе не меняет рабочий сайт.

## Если нужно вернуть предыдущую версию

Для последнего выпуска есть действие `rollback` в процессе **Tabsoff production**. Оно восстанавливает старое приложение вместе с базой до обновления. Более новые изменения на сервере при этом могут быть отменены; сохранённая вытесненная база остаётся для восстановления нужных данных. Сначала стоит разобраться, какие изменения появились после выпуска.

Portainer можно использовать для состояния контейнеров и просмотра журналов. Выпуски OpenTodo проводим через этот процесс, чтобы сохранить проверки и резервные копии.

Подробная техническая инструкция: https://github.com/tabsoff/OpenTodo/blob/tabsoff/scripts/tabsoff/README.md

## Что оптимизировано

- Убран отдельный повторный запуск полной сборки и всех тестов. Изменения приложения по-прежнему проверяются в запросе на слияние и после слияния.
- Проверки выбираются по изменённым файлам. Официальные обновления, изменения CI и неизвестные типы файлов проходят полный набор.
- Обновление, ручной откат и автоматическое восстановление после неудачного запуска проверяются на одноразовом экземпляре с вымышленными задачами.
- Версия серверного обработчика проверяется перед изменениями. Его обновление выполняется отдельно администратором и не меняет рабочее приложение.
- Старые снимки ограничены количеством и объёмом; данные и образы, необходимые для отката, сохраняются.
